# 秒杀下单方案：Lua 预占 + RocketMQ 异步 + 延迟兜底

## 一、整体架构

```
                     Controller
                         │
              ┌──────────┴──────────┐
              │                     │
         seckillVoucher()    seckillVoucherWithDB()
         (MQ 异步方案)         (纯 DB 备用方案)
              │
              v
    ┌─── SnowflakeIdWorker.nextId() ──────────┐
    │  本地雪花算法生成全局唯一 orderId（Hutool）  │
    └──────────────────────────────────────────┘
              │
              v
    ┌─── seckill-v2.lua ───────────────────┐
    │  ① 判断库存 (GET stock)                 │
    │  ② 判用户购买上限 (HGET 已购数量 < 5)      │
    │  ③ 预扣库存 (DECRBY)                    │
    │  ④ 用户购买计数+1 (HINCRBY)              │
    │  ⑤ 写 PENDING 占位 (SETEX 30min TTL)    │
    │  ⑥ 初始化重试计数器 (SETEX)              │
    │  → 返回 resultCode                     │
    └──────────────────────────────────────┘
              │
              ├──→ RocketMQ "order" 消息（即刻消费）
              │     发送失败 → 立即回退 Redis 预占
              │
              └──→ RocketMQ "delay-check" 消息（5 分钟后）
              │
              ▼ return Result.ok(orderId)    ← 立即返回给用户
```

## 二、状态机

```
订单状态流转（Redis 中存储为中文字符串，与 DB 业务状态 1~6 完全分离）：

    Lua 生成
       │
       v
  ┌─────────┐
  │  待处理  │  消费者未处理，等待 MQ 消费
  └────┬────┘
       │ Consumer 消费，claim.lua CAS 认领成功
       v
  ┌──────────┐
  │  处理中   │  消费者已认领，正在执行 DB 操作
  └────┬─────┘
       │
       ├────────── create() 成功 ──────────┐
       │                                   v
       │                            ┌──────────┐
       │                            │  已完成   │   订单成功写入 DB
       │                            └──────────┘
       │
       ├── create() 失败，retry < 3 ─────────┐
       │                                    v
       │                             ┌──────────────┐
       │                             │   重试中      │  等待 MQ 重投
       │                             └──────┬───────┘
       │                                    │ Consumer 再次认领
       │                                    v
       │                             ┌──────────┐
       │                             │  处理中   │  重新执行 create()
       │                             └──────────┘  （回到上方继续判断）
       │
       └── create() 失败，retry >= 3 ─────────┐
                                            v
                                     ┌────────────┐
                                     │  已失败     │  终态，不再处理
                                     └────────────┘
```

状态常量定义在 [OrderStatus.java](src/main/java/com/syit/hmdp/utils/OrderStatus.java)，最大重试次数 `MAX_RETRY_COUNT = 3`。

| `icr:order:` | `icr:order:2026:05:04` | String | 无（按天分 key） | Redis 自增序列号（已废弃，现由 Hutool 本地雪花算法替代） |

## 四、Lua 脚本详解

### 4.1 seckill-v2.lua — 订单预占

**调用时机**：`seckillVoucher()` 方法，同步执行

**输入**：`ARGV[1]=voucherId`, `ARGV[2]=userId`, `ARGV[3]=orderId`（由 Java 端 `RedisWorker.nextID("order")` 预生成）, `ARGV[4]=maxOrders`（每人每券最大购买数，默认 5）

**逻辑**：

```
1. GET seckill-v2:stock:{voucherId}        → 判断库存
2. HGET seckill-v2:user:{voucherId} userId → 查询已购数量
3. 已购数量 >= maxOrders                   → 返回 2（已达购买上限）
4. DECRBY seckill-v2:stock:{voucherId} 1   → 原子预扣库存
5. HINCRBY seckill-v2:user:{voucherId} userId 1 → 购买计数+1
6. SETEX seckill-v2:order:status:{orderId} → 写入"待处理"（TTL 30min）
7. SETEX seckill-v2:order:retry:{orderId}  → 初始化重试计数=0
```

**返回值**：`0` 成功，`1` 库存不足，`2` 已达购买上限（最多 `SECKILL_MAX_ORDERS_PER_USER = 5` 张）

**一人多单 vs 一人一单**：用 Hash 的 `HGET`/`HINCRBY` 替代 Set 的 `SISMEMBER`/`SADD`，每个用户对每个券可以有最多 5 次的购买额度，而不是简单的"买过就不能再买"。

> **为什么 orderId 改为 Java 生成？** Lua 5.1 的 number 类型是 double，无法精确表示 64 位雪花 ID（超过 2^53 会精度丢失），且 Redis 7 严格模式禁用了 `os` 库和位运算。改为 Java 端 `RedisWorker.nextID()` 生成后作为 ARGV[3] 传入。

**原子性保证**：整个脚本在 Redis 单线程中执行，天然的原子操作序列

### 4.2 seckill-order-claim.lua — 消费者幂等认领

**调用时机**：`VoucherOrderConsumer.handleOrder()`，每次收到 MQ 消息

**输入**：`ARGV[1]=orderId`

**逻辑**：

```
GET seckill-v2:order:status:{orderId}

  status == "待处理"   ──→  CAS 设为 "处理中"，返回 1
  status == "重试中"   ──→  CAS 设为 "处理中"，返回 1
  其他（"处理中"/"已完成"/"已失败"/不存在）──→ 返回 0
```

**关键**：多个消费者线程同时认领同一个 orderId 时，只有一个能 CAS 成功，防止重复消费。

### 4.3 seckill-order-rollback.lua — 延迟兜底回退

**调用时机**：`VoucherOrderConsumer.handleDelayCheck()`，5 分钟后触发

**输入**：`ARGV[1]=orderId`, `ARGV[2]=voucherId`, `ARGV[3]=userId`, `ARGV[4]=existsInDB`

**逻辑**：

```
Case A: existsInDB == "1"（DB 中有订单）
  → 直接设为 "已完成"，清理 retry key

Case B: existsInDB == "0" && (status=="待处理" || status=="已失败")
  → 回退：INCRBY stock +1 / 用户计数-1（count<=1 则 HDEL，否则 HINCRBY -1）
  → DEL status + retry key

其他情况（status=="处理中" 或 "重试中" 但 DB 无订单）
  → 不处理，留给消费者继续重试
```

## 五、RocketMQ 设计

### 5.1 Topic 与 Consumer Group

| 项目 | 值 | 说明 |
|---|---|---|
| NameServer | `10.1.146.45:9876` | 配置在 `application.yaml`，生产环境建议集群 |
| Topic | `voucher-order-topic` | 统一 Topic，下单和延迟检查共用 |
| Tag | `order` / `delay-check` | Broker 端按 tag 过滤，消费者不会收到不关心的消息 |
| 消费者组 | `voucher-order-consumer-group` | 两个 tag 共用同一个组，在 `onMessage` 内按 tag 分流 |
| 消费模式 | `ORDERLY` | 单线程串行，同一 Queue 内 FIFO，保证幂等认领无并发竞争 |
| 集群模式 | `CLUSTERING` | 一条消息只投给组内一个消费者，防止重复写 DB |
| 延迟级别 | `9` | 对应 5 分钟（RocketMQ 内置 1s~2h 共 18 级） |

**为什么单 Topic + Tag 而不是两个 Topic？** 下单和延迟检查同属"订单生命周期"这一业务域，不是两个独立业务。单 Topic 降低运维成本——监控、排查都在一个地方。RocketMQ 的 Tag 过滤在 Broker 端执行，消费者不会收到不匹配的消息，性能和双 Topic 一样。

**为什么 ORDERLY？** 你的 `seckill-order-claim.lua` 已经用 CAS 保证每个 orderId 只被一个消费者认领。ORDERLY 进一步保证同一条消息因重试而重复投递时不会被并发处理——幂等防护只需防"重复消费"，不用防"并发消费"。吞吐量方面，一个 Queue 串行，但 Topic 下多个 Queue 之间并行，水平扩展消费者即可。

**为什么 CLUSTERING？** 一条订单只能落库一次。若用 BROADCASTING，3 个消费者都收到同一条消息，3 个都尝试 `INSERT`，两个因主键冲突失败，浪费 DB 连接且重试计数被错误递增。CLUSTERING 下消息按 Queue 分配，每个 Queue 只归属一个消费者，天然负载均衡。

**为什么延迟 5 分钟？** 这个时间窗口需要覆盖：① MQ 重试最大耗时（约 2-3 分钟）；② DB 死锁等锁超时（MySQL 默认 50s）；③ 正常 DB 事务提交时间（< 1s）。5 分钟远超这三者之和，同时远小于 Redis 状态位 TTL（30 分钟），不会出现占位过期还没检查的情况。30s 太短（DB 可能还在重试），10 分钟太长（用户体验差）。

### 5.2 消息体（VoucherOrderMessage）

```java
// 位置: com.syit.hmdp.mq.VoucherOrderMessage
public class VoucherOrderMessage {
    private Long orderId;          // 雪花算法生成的全局唯一订单号
    private Long voucherId;        // 优惠券 ID
    private Long userId;           // 下单用户 ID
    private Long createTimestamp;  // 下单时间戳 (ms)，用于链路追踪
    private String tag;            // "order" | "delay-check"
}
```

消息通过 `RocketMQTemplate.syncSend()` 发送，序列化使用 Hutool 的 `JSONUtil.toJsonStr()`，消费者端用 `JSONUtil.toBean()` 反序列化。之所以用 JSON 而非 Java 原生序列化：可读性高，排查问题时在 RocketMQ Console 里可以直接看消息内容，不依赖 Java 版本。

延迟消息通过 `MessageBuilder.withPayload().build()` 构造 Spring Messaging 原生 Message 对象，利用 RocketMQ 的 `delayTimeLevel` 参数设置延迟级别。RocketMQ 延迟消息的实现原理：Broker 收到延迟消息后先不投递给消费者，而是写入内部延迟队列，定时任务轮询到期后再投到真实 Topic。

### 5.3 核心消息流

```
seckillVoucher()                        VoucherOrderConsumer
     │                                        │
     ├─ 发送 "order" 消息 ────────→ onMessage()
     │   （RocketMQ 即刻投递）                  │
     │                                     ├─ tag="order" → handleOrder()
     │                                     │    ├─ Lua claim: CAS 认领
     │                                     │    │    ├─ 认领失败 → 已处理，直接 ACK
     │                                     │    │    └─ 认领成功 → 继续
     │                                     │    ├─ 构建 VoucherOrder(status=1)
     │                                     │    ├─ create() @Transactional
     │                                     │    │    ├─ 成功 → Redis=已完成, ACK
     │                                     │    │    └─ 异常 → incr retry count
     │                                     │    │         ├─ retry<3 → 重试中, throw→MQ重投
     │                                     │    │         └─ retry>=3 → 已失败, ACK
     │                                     │
     │                                     └─ tag="delay-check" → handleDelayCheck()
     │                                          ├─ getById(orderId) 查 DB
     │                                          └─ rollback.lua
     │                                               ├─ DB有 → 补充标记 已完成
     │                                               └─ DB无 → 回退库存 + 删占位
     │
     └─ 发送 "delay-check" 消息 ──→ （5 分钟后才投递，兜底用）
```

两条消息在 `seckillVoucher()` 中**同时发送**，但角色不同：
- **`order` 消息**：即刻消费，承担正常流程。绝大部分订单在这一步就完成了 DB 写入。
- **`delay-check` 消息**：延迟 5 分钟投递，是安全网。只在正常流程卡住时（消费者宕机、DB 死锁重试耗尽）才真正发挥作用——回退库存或补充标记状态。

**异常处理的考虑**：order 消息发送失败时会立即回退 Redis 预占（调用 `seckill-order-rollback.lua`），返回"下单繁忙"让用户重试；delay-check 消息发送失败时只打 error 日志，不阻塞主流程——因为它的缺失不影响正常下单，只是少了一层兜底保护。

### 5.4 消息堆积与消费幂等

**消息堆积**：如果消费者宕机或处理变慢，order 消息会在 Queue 中堆积。RocketMQ 默认持久化到磁盘，重启消费者后自动从上次 commit 位置继续消费。堆积量超过阈值（建议 1000 条）时触发告警。

**幂等保证**（双重防线）：

| 防线 | 机制 | 防护场景 |
|---|---|---|
| Lua CAS 认领 | `seckill-order-claim.lua` 原子将 PENDING/FAIL_RETRYING → PROCESSING，只有一个线程成功 | MQ 重投导致的重复消费 |
| DB 主键唯一 | `tb_voucher_order.id` 主键约束，重复插入自动失败 | Lua 成功但 insert 前宕机，MQ 重投后再次 insert |

两个防线互补：Lua 防逻辑重复处理（省 DB 开销），DB 唯一索引防物理重复写入（最终兜底）。

## 七、异常场景兜底

| 场景 | 处理方式 |
|---|---|
| MQ 发消息失败 | 主动调用 `seckill-order-rollback.lua` 回退预占（库存+1、用户计数-1），返回 `"下单繁忙，请稍后重试[mq故障]"` |
| 消费者处理失败 | status → "重试中"，MQ 自动重投（最多 3 次） |
| 消费者宕机 | 5 分钟后延迟消息触发：status 仍为 PENDING → 回退库存 |
| 消费者重复消费 | Lua claim 只允许 PENDING/FAIL_RETRYING → PROCESSING 一次 |
| DB 写成功但 status 未更新 | 5 分钟后延迟消息发现 DB 有订单 → 补充设为 SUCCESS |
| 用户超过购买上限 | Lua HGET 计数（每人每券上限 5 张） + DB 查询兜底 |
| 库存超卖 | Redis DECRBY + MySQL `gt("stock", 0)` 双重防护 |

## 九、关键决策说明

1. **OrderId 在 Java 端通过 RedisWorker 预生成**：Lua 5.1 的 number 是 double 类型，无法精确表示 64 位雪花 ID（超过 2^53 精度丢失），且 Redis 7 严格模式禁用了 `os` 库和位运算。因此改为 Java 端 `RedisWorker.nextID("order")` 生成后作为 `ARGV[3]` 传入 Lua 脚本
2. **延迟消息 5 分钟**：覆盖了绝大部分 DB 写入时间（通常 < 1s）
3. **删除 BlockingQueue**：MQ 持久化离线消息，宕机不丢失；BlockingQueue 在 JVM 内存，进程死亡全丢
4. **保留 seckillVoucherWithDB() 作为降级入口**：需要手动切换 Controller 调用
5. **@Transactional 在接口方法上**：消费者通过 `IVoucherOrderService` 调用，走 Spring 代理，确保事务生效

## 十、逐环节降级措施

### 10.1 Redis 不可用（Lua 脚本执行失败）

**影响**：`seckillVoucher()` 无法执行 Lua，库存判断和预占全部失败。`stringRedisTemplate.execute()` 抛出 `RedisConnectionFailureException`，导致秒杀接口返回 500。

**已实现方案：Resilience4j 熔断器 + 降级**

```
正常链路（CLOSED）：
  请求 → seckillVoucherWithCircuitBreaker()
           → @CircuitBreaker("seckillRedis")
             → seckillVoucher() → Lua + MQ → 返回 orderId

Redis 故障，熔断打开（OPEN）：
  请求 → seckillVoucherWithCircuitBreaker()
           → @CircuitBreaker("seckillRedis") → 记录失败
           → 失败率 > 50% → 熔断器 OPEN
           → 直接走 fallback
             → @RateLimiter("dbFallback") → 20 QPS 限流
               → seckillVoucherWithDB() → 纯 DB 下单
```

**熔断器参数**：

| 参数 | 值 | 含义 |
|---|---|---|
| `sliding-window-type` | COUNT_BASED | 基于请求次数统计 |
| `sliding-window-size` | 10 | 10 次请求为一个窗口 |
| `failure-rate-threshold` | 50% | 失败率 ≥ 50% 触发熔断 |
| `wait-duration-in-open-state` | 60s | 熔断后 60s 进入半开状态 |
| `permitted-calls-in-half-open` | 3 | 半开时放行 3 次探测请求 |

**降级路径限流器参数**：

| 参数 | 值 | 含义 |
|---|---|---|
| `limit-for-period` | 20 | 每秒 20 个令牌 |
| `limit-refresh-period` | 1s | 每秒刷新 |
| `timeout-duration` | 100ms | 获取不到令牌立即失败 |

**熔断状态机**：

```
CLOSED ── 失败率 ≥ 50% ──→ OPEN ── 等 60s ──→ HALF_OPEN ── 3 次全成功 ──→ CLOSED
  ↑                                                              │
  └──────────────── 任意一次失败 ──────────────────────────────────┘
```

**代码入口**（[VoucherOrderServiceImpl.java](src/main/java/com/syit/hmdp/service/impl/VoucherOrderServiceImpl.java)）：

```java
@Override
@CircuitBreaker(name = "seckillRedis", fallbackMethod = "seckillVoucherFallback")
public Result seckillVoucherWithCircuitBreaker(Long voucherId) {
    return seckillVoucher(voucherId);  // Redis 不可达时抛异常触发熔断
}

@SuppressWarnings("unused")
private Result seckillVoucherFallback(Long voucherId, Exception e) {
    RateLimiter rateLimiter = rateLimiterRegistry.rateLimiter("dbFallback");
    if (!rateLimiter.acquirePermission()) {
        return Result.fail("系统繁忙，请稍后重试");  // 限流拒绝
    }
    try {
        return seckillVoucherWithDB(voucherId);      // 降级到纯 DB
    } catch (Exception ex) {
        return Result.fail("系统繁忙，请稍后重试");
    }
}
```

**设计要点**：

- 熔断器通过 `@CircuitBreaker` 注解实现，检测 Redis 不可达时抛出的 `RedisConnectionFailureException`
- 业务失败（库存不足、已购买）返回 `Result.fail()`，**不计入**熔断器失败统计
- 降级路径用**程序化限流**（非注解），因为注解的 `RateLimiter` 抛 `RequestNotPermitted` 会被熔断器误记为降级失败
- 恢复过程自动：半开状态放行 3 次探测，全成功 → 关闭熔断 → 恢复正常链路

#### 10.1.1 降级链路的已知局限

当前降级方法 `seckillVoucherWithDB()` 仍依赖 `seckill.lua` 做 Redis 库存校验。**Redis 真正宕机时降级路径本身也会失败**，只能返回"系统繁忙"。订单 ID 生成已改用 Hutool 本地雪花算法，不再依赖 Redis。

此外，降级路径无法实现一人多单限制：

| 能力 | Redis 正常路径 | Redis 宕机降级路径 |
|---|---|---|
| 订单 ID 生成 | `SnowflakeIdWorker.nextId()`（本地雪花） ✅ | ✅ 本地生成，不依赖 Redis |
| 库存扣减 | Lua `DECRBY` 原子 ✅ | ❌ `seckill.lua` 需要 Redis |
| 购买上限检查 | Lua `HGET` 计数 ✅ | ❌ 无 Redis 无法查 Hash |
| 异步削峰 | MQ 缓冲 ✅ | ❌ 同步写 DB |

**后续改进方向**：

```
完整的 DB-only 降级路径（剩余待实现部分）：
  1. ID 生成      → ✅ 已改用 Hutool 本地雪花算法
  2. 查已购数量    → SELECT COUNT(*) FROM tb_voucher_order
                     WHERE user_id=? AND voucher_id=?
  3. 判上限       → count >= maxOrders → 拒绝
  4. 扣库存       → UPDATE tb_seckill_voucher SET stock=stock-1
                     WHERE voucher_id=? AND stock>0
  5. 写订单       → INSERT INTO tb_voucher_order
```

关键风险：步骤 2（SELECT COUNT）和步骤 5（INSERT）之间有并发窗口，高并发下可能超限。修复方向：DB 唯一约束 + 重试，或引入独立的购买计数表 + 悲观锁。

### 10.2 RocketMQ Broker 宕机（消息发送失败）

**影响**：订单预占已成功（Redis 库存已扣 + 状态已写），但消息无法投递到消费者，订单永远不会写入 DB。

**已实现方案**：发送失败后**立即回退 Redis 预占**，调用 `seckill-order-rollback.lua` 恢复库存和用户购买计数，返回 `"下单繁忙，请稍后重试"` 让用户重新下单。

```java
// seckillVoucher() 中 [VoucherOrderServiceImpl:107-126]
try {
    // 模拟 10% MQ 发送失败，测试回退链路
    if (orderId % 10 == 0) {
        throw new RuntimeException("模拟MQ故障, orderId末位=0");
    }
    rocketMQTemplate.syncSend(...);
} catch (Exception e) {
    log.error("发送下单消息失败, 回退Redis预占, orderId={}", orderId, e);
    stringRedisTemplate.execute(
        SECKILL_ORDER_ROLLBACK_SCRIPT,    // 回退库存+用户计数+清理状态
        Collections.emptyList(),
        String.valueOf(orderId),
        String.valueOf(voucherId),
        String.valueOf(userId),
        "0"                                 // existsInDB = "0"
    );
    return Result.fail("下单繁忙，请稍后重试[mq故障]");
}
```

10% 的模拟故障（`orderId % 10 == 0`）仅用于测试验证回退链路，生产环境应移除。

### 10.3 消费者宕机（消息堆积）

**影响**：MQ 消息堆积，PENDING 状态的订单 5 分钟内无人处理。

**措施**：
- **自动兜底**：5 分钟后延迟消息触发，status 仍为"待处理" → Lua 回退库存，用户重试即可。
- **监控告警**：MQ 消息堆积量 > 阈值时告警，重启消费者节点。
- **快速恢复**：消费者重启后批量消费堆积消息，正常写入 DB。

### 10.4 DB 写入异常（MySQL 宕机或死锁）

**影响**：`create()` 抛出异常，MQ 重投，retry count 递增。

**措施**：
- **自动重试**：retry < 3 次，status → "重试中"，MQ 重投。
- **重试耗尽**：retry >= 3，status → "已失败"，ACK 不再处理。
  - 5 分钟后延迟消息发现"已失败"且 DB 无订单 → 回退库存。
  - DB 恢复后，可在管理后台根据 FAIL_FINAL 订单列表手动补偿。
- **死锁优化**：`create()` 中先 UPDATE 再加 INSERT 的顺序已经降低了死锁概率（先拿 SeckillVoucher 的行锁，再插入 VoucherOrder）。

### 10.5 Redis 成功但 DB 写成功 status 未更新

**影响**：DB 中有订单，Redis status 不是"已完成"（消费者在 set status 前宕机）。

**措施**：
- **自动兜底**：5 分钟后延迟消息 `getById(orderId)` 查到 DB 有订单 → 补充设 Redis status 为"已完成"。
- **定期对账**：定时任务扫描 `tb_voucher_order` 中 `createTime < now - 10min` 且 Redis status 不是 SUCCESS 的订单，补充更新。

### 10.6 库存不一致（Redis vs MySQL 库存漂移）

**影响**：回退失败、TTL 过期孤儿占位等导致 Redis 库存 > DB 实际库存，后续可能超卖。

**措施**：
- **TTL 兜底**：status key 30 分钟后自动过期，预留库存自动释放。
- **定时对账**：每小时用 DB 真实库存矫正 Redis 库存：
  ```sql
  -- DB 真实库存
  SELECT stock FROM tb_seckill_voucher WHERE voucher_id = ?
  -- Redis 当前库存
  GET seckill-v2:stock:?
  -- 若差值 > 阈值，以 DB 为准矫正 Redis
  ```
- **安全边界**：Redis 预扣的库存量不会超过 DB 真实库存，因为预热时 `SET stock = dbStock`。

### 10.7 启动预热失败

**影响**：Redis 中没有库存数据，`seckill-v2.lua` 读到 nil → 返回库存不足。

**措施**：
- **启动检查**：`@PostConstruct` 中预热完成后检查 Redis key 是否存在，不存在则重试或告警。
- **懒加载兜底**：Lua 中 `GET stock` 返回 nil 时，不从 DB 回源（防止缓存击穿），但可以做一次 DB 回源写回 Redis：
  ```lua
  -- 扩展 Lua 逻辑
  if (not stock) then
      -- 尝试从 DB 加载（需配合 Java 侧提前写入）
      return {-1, 0}  -- 特殊 code：库存未预热
  end
  ```
  Java 侧收到 `-1` 后调用预热逻辑再重试。

### 10.8 雪花算法时钟回拨

**影响**：Hutool 本地雪花算法依赖系统时钟。如果服务器发生时钟回拨，可能产生重复 ID。

**措施**：
- Hutool 的 `Snowflake` 默认使用 `SystemClock`（基于 `ScheduledExecutorService` 每秒缓存时间戳），小幅度回拨会被缓存时间掩盖
- 若回拨超过 1 秒，`nextId()` 会抛 `RuntimeException`，需人工介入或 NTP 时钟同步修复
- 数据库 `tb_voucher_order.id` 主键唯一约束提供最终兜底

### 10.9 降级优先级总结

| 优先级 | 场景 | 降级策略 | 实现状态 |
|---|---|---|---|
| P0 | Redis 不可用 | Resilience4j `@CircuitBreaker` 自动熔断 + 20 QPS 限流 + 切纯 DB 方案 `seckillVoucherWithDB()` | **已实现** |
| P1 | RocketMQ 不可用 | 返回 fail "下单繁忙"，Lua 回退库存，用户重试 | 已实现 |
| P2 | 消费者宕机 | 延迟消息兜底 + MQ 堆积告警 | 已实现 |
| P3 | DB 瞬时异常 | MQ 自动重试，5min 内恢复即可 | 已实现 |
| P4 | 库存漂移 | TTL 兜底释放 + 定时对账矫正 | 待实现 |

### 10.10 监控指标建议

| 指标 | 含义 | 告警阈值 |
|---|---|---|
| MQ 消息堆积量 | `voucher-order-topic` 积压条数 | > 1000 |
| PENDING → PROCESSING 延迟 | 从 Lua 生成到消费者认领的时间差 | > 10s |
| FAIL_FINAL 数量 | 重试耗尽订单数 | > 0（出现即告警） |
| Redis-DB 库存偏差 | `abs(RedisStock - DBStock)` | > 5 |
| create() 成功率 | `已完成 / (已完成 + 已失败)` | < 99% |

## 十一、用户体验：先给号再确认的问题与改进

### 11.1 当前体验

```
用户                    系统
 │  ── 点击下单 ──→
 │                  Lua 预占 + MQ 投递
 │  ←── orderId ────  （用户以为下单成功）
 │
 │  …… 几秒后 ……
 │
 │  ── 查看我的订单 ──→
 │                    DB 查询
 │  ←── 不存在！ ─────  （写 DB 失败，已被回退）
 │
用户心态：我明明下单成功了，订单号都拿到了，怎么没了？
```

### 11.2 为什么会这样

这是一个**架构取舍**——用"先给号"换取极致响应速度：
- 同步等 DB → 用户体验好但慢，高并发下 DB 扛不住
- 异步先给号 → 响应极快但存不一致

所有异步秒杀方案都有这个 trade-off，没有完美的解法，只有优化。

### 11.3 改进措施

**方案 A（最小改动）：返回明确的"处理中"语义**

```java
// 不要返回 Result.ok(orderId)，改为：
Map<String, Object> data = new HashMap<>();
data.put("orderId", orderId);
data.put("status", "ordering");    // 告知前端：还在处理
data.put("message", "正在为您下单，请稍后查看");
return Result.ok(data);
```

前端收到后不显示"下单成功"，而是显示"处理中，预计 3 秒出结果"。

**方案 B：前端轮询状态（推荐，可实现）**

提供一个订单状态查询接口：

```java
// 新加 Controller 方法
@GetMapping("/seckill/order-status/{orderId}")
public Result orderStatus(@PathVariable Long orderId) {
    // 1. 先查 Redis 状态
    String status = stringRedisTemplate.opsForValue()
        .get(SECKILL_V2_ORDER_STATUS_KEY + orderId);
    if (status != null) {
        return Result.ok(Map.of("status", status));
    }
    // 2. Redis 已过期，查 DB
    VoucherOrder order = voucherOrderService.getById(orderId);
    if (order != null) {
        return Result.ok(Map.of("status", "已完成"));
    }
    return Result.fail("订单不存在");
}
```

前端收到 orderId 后每 500ms 轮询一次，最多 5 秒：

```
status == "待处理" → 显示"排队中..."
status == "处理中" → 显示"下单处理中..."
status == "已完成" → 显示"下单成功！"  ✓
status == "重试中" → 显示"下单处理中..."
status == "已失败" → 显示"下单失败，请重试"
status == null && DB 无 → 显示"下单失败"  ⚠
```

**方案 C（体验最好，成本最高）：WebSocket 推送**

消费者 `SUCCESS` 或 `FAIL_FINAL` 后，通过 WebSocket 把最终结果推送给对应用户，前端无需轮询。

### 11.4 用户体验对比

| 方案 | 实现成本 | 用户体验 |
|---|---|---|
| 当前方案 | ✅ 无 | ❌ 用户可能查到空订单 |
| A. 返回"处理中"语义 | 极低（改一行代码） | ⚠️ 用户至少不会误以为成功 |
| B. 前端轮询 | 低（加一个查询接口） | ✅ 用户 3-5 秒内知道结果 |
| C. WebSocket 推送 | 高（需要 WS 基础设施） | ✅✅ 实时推送，体验最好 |

### 11.5 建议

至少实施 **A + B**：把返回值语义改了，再加个状态查询接口，成本很低但体验提升很大。
