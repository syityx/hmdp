# 缓存方案：Bloom Filter 前置拦截 + 逻辑过期 + 互斥锁重建

## 一、整体架构

```
请求 shop:id=123
     │
     ▼
┌── BloomFilterHelper.contains("123")
│   ├─ isEmpty? ───→ 跳过拦截（过滤器刚建/被误删，避免误杀合法请求）
│   ├─ false ───→ return "店铺不存在"（一定不存在，零 DB 开销）
│   └─ true ────→ 继续 ↓
│
     ▼
┌── CacheClient.queryWithLogicalExpire("cache:shop:123")
│   │
│   ├─ Redis 命中 & 未过期 ─→ 直接返回
│   │
│   ├─ Redis 命中 & 已过期 ─→ 抢 Redisson 分布式锁
│   │   ├─ 抢到 ─→ Double Check ─→ 查 DB ─→ setWithLogicalExpire 重建
│   │   └─ 未抢到 ─→ 返回旧数据（过期但可用）
│   │
│   └─ Redis 未命中（key 被意外删除）──→ 互斥锁重建
│       ├─ 抢到 ─→ Double Check ─→ 查 DB ─→ 重建
│       └─ 未抢到 ─→ sleep 50ms ─→ 递归重试
│
     ▼
  返回结果 or "店铺不存在"
```

## 二、三层防线对比

| 防线 | 组件 | 解决的问题 | 关键技术 |
|------|------|-----------|---------|
| **L1** | `BloomFilterHelper` | 缓存穿透（恶意/意外请求不存在的 ID） | Redisson `RBloomFilter` |
| **L2** | `CacheClient.queryWithLogicalExpire` | 缓存击穿（热点 key 过期瞬间大量请求压 DB） | 逻辑过期 + Redisson 分布式锁 |
| **L3** | 空值缓存 `""` | 缓存穿透（DB 中不存在的数据） | 短 TTL 空字符串（`CACHE_NULL_TTL=2s`） |

## 三、核心组件

### 3.1 BloomFilterHelper

**文件**：`src/main/java/com/syit/hmdp/utils/BloomFilterHelper.java`

封装 Redisson `RBloomFilter`，提供：

| 方法 | 作用 |
|------|------|
| `getFilter(name, n, p)` | 获取/懒创建过滤器，`tryInit` 幂等 |
| `add(name, key, n, p)` | 添加元素 |
| `contains(name, key, n, p)` | 查询元素是否可能存在 |
| `isEmpty(name, n, p)` | 过滤器为空（`count()==0`），用于误删容错 |

**配置**（`RedisConstants`）：

```java
BF_SHOP_KEY      = "bf:shop"      // Redis key
BF_SHOP_EXPECTED = 10_000L        // 预计元素数
BF_SHOP_FPR      = 0.01           // 误判率 1%
```

**内存估算**：n=10000, p=0.01 → m≈95850 位 ≈ 12 KB。

**Redis 存储**（Redisson 自动管理）：

| Key | 类型 | 说明 |
|-----|------|------|
| `bf:shop` | String（位数组） | 位图本体，`SETBIT`/`GETBIT` 操作 |
| `{bf:shop}:config` | Hash | 元数据：`size`, `hashIterations`, `expectedInsertions`, `falseProbability` |

**容错机制——isEmpty 守卫**：

```java
// 过滤器为空时跳过拦截，防止 bf key 被误删后合法请求被拒绝
if (!bloomFilterHelper.isEmpty(...)
        && !bloomFilterHelper.contains(...)) {
    return Result.fail("店铺不存在");
}
```

触发条件：Redis 中 `bf:shop` key 不存在或 `count()==0`。
恢复路径：跳过拦截 → 请求正常走 cache/DB → 预热或后续 `add` 逐步重建过滤器。

### 3.2 CacheClient

**文件**：`src/main/java/com/syit/hmdp/utils/CacheClient.java`

提供 4 种缓存查询策略：

| 方法 | 锁机制 | 适用场景 |
|------|--------|---------|
| `queryWithRedis` | 无锁 | 不解决击穿，仅解决穿透 |
| `queryWithSynchronzied` | `synchronized` + `String.intern()` | 单 JVM，简单互斥 |
| `queryWithReentrantLock` | `ReentrantLock` + `ConcurrentHashMap` | 单 JVM，支持 tryLock 非阻塞 |
| `queryWithRedissonLock` | Redisson 分布式锁 + 重试 | 多 JVM，watchdog 自动续约 |
| `queryWithLogicalExpire` | 逻辑过期 + Redisson 锁（**当前主用**） | 热点 key 高并发 |

#### 逻辑过期方案详解（queryWithLogicalExpire）

核心思想：**Redis key 不设物理 TTL，只存逻辑过期时间**，避免 TTL 到期瞬间大量请求穿透。

1. **key 存在且未过期** → 直接返回（常态路径，零锁）
2. **key 存在但已过期** → 抢分布式锁重建；未抢到锁的返回旧数据（兜底）
3. **key 不存在**（被误删/未预热） → 互斥锁重建（自愈）
4. **重建时 DB 返回 null** → 写入空字符串 `""`（防穿透，TTL=2s）

**关键参数**：

| 常量 | 值 | 说明 |
|------|---|------|
| `CACHE_SHOP_KEY` | `cache:shop:` | 缓存 key 前缀 |
| `LOCK_SHOP_KEY` | `lock:shop:` | 分布式锁 key 前缀 |
| `CACHE_NULL_TTL` | 2s | 空值缓存 TTL |
| 逻辑过期时间 | 5s | `setWithLogicalExpire` 的参数 |

## 四、预热策略

`ShopServiceImpl.preheatShopCache()` → `@PostConstruct` 启动时执行：

```
加载全部 Shop → 遍历：
  ├─ setWithLogicalExpire(key, shop, 5s)   → Redis 缓存（无物理 TTL）
  └─ bloomFilterHelper.add(key, id, ...)   → Bloom Filter 位数组
```

预热时单条失败不影响整体（独立 try-catch），输出统计：`缓存 X 条，布隆 Y 条`。

预热的作用：
- **Bloom Filter 初始化**：没有预热时过滤器为空，所有请求会被跳过拦截（非致命），但失去 L1 防御
- **冷启动性能**：避免前 N 个请求都走锁竞争 + DB 查库

## 五、数据一致性

`ShopServiceImpl.update(Shop shop)` — `@Transactional`：

```
updateById(shop)                           // 1. 先更新 DB
stringRedisTemplate.delete(CACHE_SHOP_KEY)  // 2. 删除缓存（不操作 Bloom Filter）
```

- **删缓存而非更新**：避免并发写导致的缓存与 DB 不一致
- **不删 Bloom Filter**：shop 仍存在，下次查询缓存 miss → 逻辑过期重建 → 缓存恢复

## 六、Redis Key 一览

| Key | 类型 | 说明 |
|-----|------|------|
| `cache:shop:{id}` | String (JSON) | 逻辑过期缓存，`RedisData{data, expireTime}` |
| `lock:shop:{id}` | Redisson Lock | 缓存重建互斥锁 |
| `bf:shop` | String (bitmap) | Bloom Filter 位数组 |
| `{bf:shop}:config` | Hash | Bloom Filter 元数据 |
